# 2026-W36

## Incident: Tier-2 Drafting Fabricated a Player and Stats With No Matched Data (2026-08-31)

**Type:** Incident or near-miss.

**Summary.** A tier-2 X reply draft injected a fabricated player ("Omar Cooper
Jr.," 13% boom / 18% bust) into an OBJ-signs-with-Giants narrative. The player
has no real connection to the story (he's a Jets WR). Draft was never posted
(tier 2, `can_reply_via_api: false`) — no external exposure, but it reached
the Telegram approval queue with confident, specific-sounding fake numbers.

**Original diagnosis (incorrect).** The initial write-up attributed this to
`x-monitor.R`'s prospect-name matcher firing on an irrelevant player and the
drafting step weaving that real-but-irrelevant match into a false causal
narrative, proposing a team-relevance check on the matcher as the fix.

**Actual root cause.** Reviewed `openclaw-scripts/x-monitor.R:751-785`
directly against the source tweet text ("From @GMFB: Odell Beckham Jr makes
the #Giants."):
- "cooper" has been in the fallback last-name exclusion list
  (`x-monitor.R:771`) for a long time — predates this incident, confirmed via
  `git log -p`.
- The primary full-name loop requires the literal string "omar cooper jr" in
  the tweet text. It isn't there.
- Tier 2 doesn't even use `quoted_text` in scoring (`combined_text` is
  tier-1A/1B only) — only `tweet$text` is checked.

Conclusion: `prospect_match` was `FALSE` and `matched_prospect` was `NULL`
for this tweet. The player name and stats never entered `x-monitor.R`'s
candidate JSON at all. The drafting LLM — which runs on the OpenClaw side
using `prompts/x_reply_tier_2.md`, not in the autopilot repo — fabricated
both the identity and the stats with zero grounding data behind them. This
is a worse failure mode than an irrelevant-but-real match: it's an
unconstrained hallucination, not a bad inference from real data.

**Fix applied (autopilot repo, commit pending as of this entry).**
1. `openclaw-scripts/x-monitor.R` — added a validity guard so prospect
   fields are only attached to candidate JSON when the matched row's
   `player_name`/`p_boom`/`p_bust` are non-NA, with a stderr warning if not.
   This wasn't the cause here (the invariant already held structurally) but
   it closes a previously-unenforced gap for future refactors.
2. `prompts/x_reply_tier_2.md` — added an explicit grounding rule: never
   name a player, team move, or stat not present in the tweet text or
   `{model_data}`; never infer a causal roster narrative connecting a
   `{model_data}` player to a transaction unless the tweet itself states the
   connection; return "SKIP" over guessing.

**Not fixed (outside autopilot repo).** The actual drafting call — the
OpenClaw-side step that reads `draft_prompt_path` and calls the LLM — isn't
in this repo, so its behavior around empty/absent `model_data` couldn't be
directly inspected or hardened from here. The prompt-file fix above should
constrain it, but whoever owns that drafting code should verify:
- What `{model_data}` actually gets interpolated as when `prospect_match`
  is `FALSE` (empty string? omitted? literal "null"?) — an ambiguous
  placeholder is exactly what invites this kind of fabrication.
- Whether there's room for a second-pass validation step (does every player
  name/stat in the drafted reply trace back to `model_data` or the tweet
  text?) before a draft reaches the Telegram queue.

**Verification owed.** Whoever owns the OpenClaw drafting step to confirm
the `{model_data}` interpolation behavior above and consider the
validation-pass follow-up.

## Feature: x-monitor.R Now Matches Veteran Players via boxscore-prophet (2026-08-31)

**Type:** Configuration change / scheduled-task logic change.

**Summary.** `x-monitor.R`'s prospect matcher previously only covered 2026
draft-class rookies (`nfl-draft-model`), so any tweet about an established
veteran got no model grounding at all -- correct after the fabrication fix
above, but a real analytical-coverage gap given most tier-1B/1C/2 NFL
Twitter coverage is veteran-skewed. Earnest requested wiring in
boxscore-prophet's weekly QB/RB/WR/TE slate as a second, independent match
source.

**Details.** `openclaw-scripts/x-monitor.R` (commit pending as of this
entry) adds:
- `load_veteran_slate()` -- reads `~/boxscore-prophet/output/latest/scored_slate.csv`
  and `run_manifest.json`. Soft-optional, same pattern as `MODEL_DATA`:
  missing file, unreadable manifest, or `generated_at` older than 8 days
  (offseason, mid-refresh, sibling repo not checked out) all resolve to
  `NULL` rather than erroring the scan.
- A full-name-only match against `player_name` in `score_tweet()`,
  deliberately with **no** last-name fallback -- the veteran pool is ~900
  rows vs. ~30 in the draft-prospect fallback list, so a surname matcher
  here would reintroduce the collision risk the earlier incident was about,
  at much larger scale.
- Matched rows attach `veteran_name/position/team/p_start/p_boom/`
  `p_boom_recal/pred_vol/pred_tot` to candidate JSON, gated by the same
  NA-field validity guard added in the fabrication-fix commit.
- `has_analytical_hook()` (tier-1C gating) now also counts a veteran match
  as an analytical hook, same as a prospect match.

**Verification.** Confirmed against real production data (not synthetic
fixtures): copied an actual `boxscore-prophet/output/10c_scored_slate_2025_w15.csv`
into a scratch `output/latest/`, generated a real-shaped `run_manifest.json`,
and ran the loader/matcher logic standalone. Verified: loads and matches a
real player name (Justin Herbert, LAC, p_start=0.352) against a synthetic
tweet; correctly returns no match for a tweet naming an unrelated player
(the OBJ/Giants tweet from the fabrication incident); correctly returns
`NULL` for a stale (2026-01-01) manifest and for a missing directory; the
NA-field guard correctly rejects a row with `NA` `player_name`. Full
`score_tweet()` was not exercised end-to-end (requires live X API
credentials), but the new logic added to it is a small, isolated block
around already-proven matching machinery.

**Not done.** Same gap as the fabrication-fix entry above: whichever
OpenClaw-side code assembles `{model_data}` for the drafting prompt needs
to be told about the new `veteran_*` candidate fields -- that wiring is
outside the autopilot repo and wasn't touched here.

**Rollback.** Revert the commit; `veteran_data` is additive and optional,
so no state migration is needed either direction.
