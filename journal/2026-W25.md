### Bug: Earnest Not Reading Surfacing Log on Inline Button Callbacks

## Type
- [x] Bug fix

## Summary
When Steve taps an inline button on an x-monitor reply candidate (`fb:{tweet_id}:{bucket_code}`), Earnest handles the callback blind — she doesn't look up the draft text or candidate metadata from `~/autopilot/data/x-monitor-surfacings.jsonl`, even though that file has everything she needs. This causes two downstream failures:

1. **Earnest asks Steve to paste the reply text** she already has on disk (happened twice today, 2026-06-15 — both Schefter tweets)
2. **Feedback log not written** — `data/x-monitor-feedback.jsonl` has no entries for any of today's callbacks (three skips, two confirms)

## Root Cause

Earnest's `fb:` callback handler does not read `x-monitor-surfacings.jsonl`. It only parses the `tweet_id` and `bucket_code` from the callback string and then asks Steve for context it already has.

Confirmed: the surfacing log correctly contains the Tippmann draft (message_id 4936, tweet_id `2066523217569702391`):
```json
{
  "tweet_id": "2066523217569702391",
  "username": "AdamSchefter",
  "tier": "1C",
  "can_reply_via_api": false,
  "draft": "$16.6M APY is near the top for interior OL. At 52% guaranteed...",
  "message_id": 4936
}
```
That is word-for-word what Steve posted. Earnest never looked it up.

## Required Fix (Earnest's callback handler)

On every `fb:{tweet_id}:{bucket_code}` callback, before doing anything else:

1. **Look up the surfacing log:**
   ```r
   # pseudocode
   lines <- readLines("~/autopilot/data/x-monitor-surfacings.jsonl")
   records <- lapply(lines, jsonlite::fromJSON)
   match <- Filter(function(r) r$tweet_id == tweet_id, records)
   candidate <- if (length(match)) tail(match, 1)[[1]] else NULL
   ```

2. **Extract context from the match:**
   - `candidate$draft` — the reply text that was sent to Steve
   - `candidate$username` — source account handle
   - `candidate$tier` — tier label
   - `candidate$can_reply_via_api` — whether the API post is expected to work
   - `candidate$draft_style` — for logging

3. **On `:c` (confirm / posted as-is):**
   - Attempt API post if `can_reply_via_api == TRUE`; handle 403 gracefully (log as `failed_restricted`, notify Steve to post manually)
   - Append to `replies` Google Sheet tab (same schema as existing manual entries): date, account, replied_to_tweet URL, our_reply (from `candidate$draft`), method (`api` or `steve_manual`), notes
   - Call `x-feedback-log.sh` with the standard feedback JSON (`bucket_code: "c"`)
   - Send confirmation to Steve ("✓ Logged and posted" or "✓ Logged — post manually, Schefter has reply restrictions")

4. **On `:s` (skip):**
   - Call `x-feedback-log.sh` with `bucket_code: "s"`
   - No further action (current behavior of silent acknowledgment is fine)

5. **Fallback (no match in surfacing log):**
   - Current behavior: ask Steve for the text
   - This should be rare — only if the surfacing log was somehow not written at send time

## Secondary Fix: `can_reply_via_api` Flag

The surfacing log already has `"can_reply_via_api": false` for all Tier-1C accounts (Schefter, Shams, Woj). Earnest should check this flag before attempting the API post and skip straight to "post manually" notification if false. No point burning an API call that will always 403.

The 403 error message received today:
```
"Reply to this conversation is not allowed because you have not been mentioned or otherwise engaged by the author of the post you are replying to."
```
This is a permanent restriction on these accounts (they have reply settings locked to followers/verified), not a transient error. The flag correctly captures this.
