4. The dual-mirror setup (`~/.openclaw/workspace/scripts/` and `~/autopilot/openclaw-scripts/`) created drift risk. Single source of truth removes that.

### Asymmetric Polling Cadence: Fast Lane + Slow Lane (Bundle #2)

## Type
- [x] Scheduled task added or modified
- [x] Configuration change

## Summary
Splits the single x-monitor cron job into a fast lane (tier 1A/1B/1C, every 30 min during waking hours) and a slow lane (tier 2, every 3 hours on the existing schedule). Freshness is the strongest reply-engagement signal in our hit-rate analysis, and the old 3-hour cadence let tier-1 tweets age out of their reply window before surfacing.

## Details

### Autopilot commit (prereq)
- `x-monitor.R` `--tier` flag now accepts a comma-separated set
  (`--tier 1A,1B,1C`) in addition to a single tier (`--tier 1A`).
- Single-tier behavior is unchanged; the comma form is additive.
- Parse-tested locally on laptop pre-commit.

- Command: previously called `~/.openclaw/workspace/scripts/x-monitor.sh`,
  updated in the W24 first entry to `~/autopilot/openclaw-scripts/x-monitor.sh`.
- Action: **delete** after the two new jobs below are running.

### New cron job: x-monitor-fast (tier 1A + 1B + 1C)
- Schedule: `0,30 5-22 * * *` America/New_York
- Frequency: every 30 min, 5:00 AM through 10:30 PM ET (36 runs/day).
- Command: `cd ~/autopilot && bash openclaw-scripts/x-monitor.sh --tier 1A,1B,1C --hours 1`
- Accounts covered: the 14 tier-1 handles (4 + 6 + 4).
- Lookback: 1 hour matches the 30-min cadence — fresh tweets only,
  generous overlap as a missed-poll safety buffer.

### New cron job: x-monitor-slow (tier 2)
- Schedule: `0 5,8,11,14,17,20 * * *` America/New_York (existing slow schedule preserved)
- Frequency: 6 runs/day, 5 AM through 8 PM ET.
- Command: `cd ~/autopilot && bash openclaw-scripts/x-monitor.sh --tier 2 --hours 3`
- Accounts covered: all monitor-list handles without a `[tier:1X]`
  annotation (~28 accounts).
- Lookback: 3 hours matches the 3-hour cadence.

## Why
1. Freshness drives reply engagement. Steve's own hit-rate read on the prior system: ~15-20% surfaced candidates engaged with, but "when I reply in a timely fashion when the post is very new, I get very good engagement. When it is stale, the engagement is worse."
2. The 3-hour cadence meant a Schefter scoop posted at 8:05 AM didn't surface until 11:00 AM, by which point the reply window had closed. Tier-1 accounts deserve a polling cadence that respects this.
3. Tier-2 accounts don't benefit from the same cadence — most surfacings tied to article keyword overlap, which isn't time-sensitive on the same scale.
4. Splitting lanes lets us scale costs predictably: fast lane is 14 accounts * 36 runs/day; slow lane is ~28 accounts * 6 runs/day.

## Cost note
Rough estimate: 3-5x current API spend (which was running ~$5-15/month per W17 entry), so likely $30-50/month total. Steve approved this spend ceiling during scoping. Validate against actual day-1 spend on the X dev account and tune `--hours` / cadence if it materially overshoots.

### Feedback Bucketing via Telegram Inline Buttons (Bundle #3)

## Type
- [x] Feature added
- [x] Scheduled task added or modified

## Summary
Adds three inline feedback buttons (Skip / As-is / Edited) to every x-monitor candidate that gets sent to Telegram. A new cron-driven poller captures the button clicks and appends them to a JSONL feedback log, joinable to the surfacing log by `tweet_id`. After a few weeks of data we can measure per-account hit rate, per-tier edit rate, and time-of-day patterns to validate (or refute) the freshness hypothesis and the tier-architecture decisions.

## Details

### Autopilot changes
- New file: `openclaw-scripts/x-feedback-send.R` -- reads `{"candidate": {...}, "draft": "..."}` from stdin, formats a Telegram message, attaches an `inline_keyboard` with three buttons whose `callback_data` is `fb:{tweet_id}:{bucket_code}` (s/c/e), and appends a record to `data/x-monitor-surfacings.jsonl`. Emits `{"ok": true, "message_id": N}` on success.
- New file: `openclaw-scripts/x-feedback-send.sh` -- env-injected wrapper around the R script.
- New file: `openclaw-scripts/x-feedback-poll.R` -- calls Telegram `getUpdates` with offset tracking, processes any `callback_query` events whose data starts with `fb:`, appends to `data/x-monitor-feedback.jsonl`, and calls `answerCallbackQuery` so the Telegram button clears its loading spinner.
- New file: `openclaw-scripts/x-feedback-poll.sh` -- env-injected wrapper around the R script.
- Updated `.gitignore` to exclude the three new state files (`data/x-monitor-surfacings.jsonl`, `data/x-monitor-feedback.jsonl`, `data/x-feedback-poller-state.json`).
- Updated `openclaw-scripts/README.md` to document both scripts and the new state-file locations.

### Schema

`data/x-monitor-surfacings.jsonl` -- one JSON object per line, written each time `x-feedback-send.R` ships a candidate:
```
{
  "timestamp_utc": "2026-06-13T19:42:11Z",
  "tweet_id":      "1234567890123456789",
  "username":      "ColinCowherd",
  "tier":          "1A",
  "is_cowherd":    true,
  "draft_style":   "tier_1a_cowherd",
  "draft_prompt_path": "prompts/x_reply_tier_1a_cowherd.md",
  "reason":            "velocity_override",
  "engagement_status": "cold",
  "can_reply_via_api": false,
  "minutes_old":         12.4,
  "engagement_per_min":  247.3,
  "relevance_score":     1,
  "prospect_match":      false,
  "draft":               "...the drafted reply...",
  "message_id":          7891
}
```

`data/x-monitor-feedback.jsonl` -- one JSON object per line, written each time `x-feedback-poll.R` ingests a callback:
```
{
  "timestamp_utc": "2026-06-13T19:43:55Z",
  "tweet_id":      "1234567890123456789",
  "bucket":        "posted_edited",
  "bucket_code":   "e",
  "update_id":     94837284,
  "callback_id":   "94837284:1",
  "message_id":    7891,
  "chat_id":       "8676616323",
  "from_user":     "merrittocratic"
}
```

Join the two logs on `tweet_id` (and optionally `message_id`) to compute per-account, per-tier, time-of-day hit rates.

### Cowherd-style choice
Plain text in the Telegram message (no `parse_mode`). Tweet text and drafts can contain Markdown landmines (`*`, `_`, backticks) that would otherwise need defensive escaping. The existing `R/00_config.R` `notify_telegram` already learned this lesson the hard way; the new send script avoids the problem entirely.

## Why
Steve's earlier feedback explicitly named the gap:

> "The manual copy/pasting does occur, but I don't think the feedback mechanism is right to know when I am actually posting/replying with [what he] suggests or post/replying with edits. Feels like we need to bucket that a little. 'Not worth replying/posting', 'Replied/posted as is', 'Replied/posted, but with edits'."

Without this loop, we have no signal on whether the tier-architecture and prompt-template changes from Bundles #1 and #2 are actually moving the needle. Three buckets give us:

| Bucket | Signal |
| --- | --- |
| Skip | Surfacing was wrong (stale, off-topic, bad account) |
| As-is | Both surfacing AND draft worked |
| Edited | Surfacing worked, draft needs tuning |

After a few weeks of logs, per-account skip rates flag tier-2 handles worth pruning, per-tier edit rates flag prompt templates worth iterating, and time-of-day patterns confirm or refute the freshness hypothesis baked into Bundle #2.

## Jobs retired in this amendment
- `x-monitor-noon` -- schedule `30 12 * * 1-5`, weekday-only 12:30 PM, no `--tier` flag (all tiers).
- `x-monitor-evening` -- schedule `0 19 * * 1-5`, weekday-only 7:00 PM, no `--tier` flag.

## Why retire
1. **Redundant coverage.** Every time slot these four hit is already hit by fast lane (tier 1) or slow lane (tier 2), with the single exception called out below.
2. **Wasted API spend.** Each duplicate fetch is a billable X API read with no new candidate signal -- the `seen_tweet_ids` dedup in `x-monitor.R` prevents re-surfacing the same tweet, so the extra reads buy nothing.
3. **State-file write race.** Multiple jobs firing in the same minute write to `~/.openclaw/workspace/memory/x-monitor-state.json` concurrently. Race risks: lost `seen_tweet_ids` (re-surfacing the same tweet) or lost `daily_candidate_count` (overshooting the 8/day cap).

## Coverage gap acknowledged
The only time slot lost by retiring all four is **weekend 11:00 PM ET** (the `x-monitor-weekend` 23:00 fire). Fast lane currently ends at 22:30 (`0,30 5-22 * * *`). Sports news is quiet overnight, so the gap is accepted as a deliberate tradeoff. If real-world reply-engagement data ever shows weekend late-night opportunities being missed, the fix is a one-line cron amendment to extend the fast lane to `0,30 5-23 * * *` (38 fires/day vs 36) -- no code changes needed.
